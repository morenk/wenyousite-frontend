本报告对应应用源码 `68bbfa2e87956214b3de4cfbbd7b0b8ff5a73f28`、候选 BuildID `65KMA0h5JEzFnhy5OS0QT`。记录一次受控验收，不代表公网已发布状态。播放策略见[首页模块](modules/home.md#11-列表动图封面)，[原始逐点样本](cover-playback-performance.samples.json)可核对基线、进程类型、采样次数与峰值。

## 方法与适用边界

- VPS Linux 上使用 Playwright 1.62.0 的 headless Chromium，1 worker，仓库现有 `pnpm test:e2e:candidate e2e/thread-cover-performance.spec.ts` 管理候选服务。复用上述生产构建，未重建/部署应用；图片和 API 全部来自本地 fixture。
- 视口为 `1440 × (600 + 数量 × 340)`，保留真实卡片布局并使 4/8/12 张同时可见，是扩展视口压力场景，不是普通 PC 或手机屏幕。同一帧序列的 480×270、12 帧 GIF 为 736785 bytes，WebP 为 85890 bytes；构造素材压缩率不能代表真实论坛素材。
- 每组先关闭动画并等静态 poster 就绪，静止 150ms 后取进程基线，再允许播放；采样覆盖资源开始加载、所有目标元素可见和随后约 1200ms 的播放观察窗。热组使用同一页面缓存和自然内存状态，不强制 GC 或清空解码缓存。
- 使用本次 Playwright browser 的 `SystemInfo.getProcessInfo` 获取 PID/类型，只读取这些 PID 的 `/proc/PID/smaps_rollup`。本次可归属 browser、renderer、GPU、network.mojom.NetworkService 四类；不把未被 CDP 枚举的 zygote/crashpad、系统缓存或物理显存纳入统计，也不称为整机内存。
- 采样目标间隔 150ms，实际循环还包含 CDP 与 /proc 读取时间。表中列出实际样本数和观察跨度；短暂分配峰值可能落在采样之间，因此只称“观察峰值”。各进程读取也不是同一时刻的原子快照。
- RSS 合计可能重复计算跨进程共享页；PSS 按共享份额分摊，更适合看合计，但也会受其他共享相同内存页的进程影响。Playwright 复用 browser，页面 renderer 生命周期和浏览器缓存可能跨组保留；不同组绝对基线不可直接当格式因果对比。
- 进程增量同时包含页面、图片解码、缓存、合成、脚本及采样开销，不能当精确动画 decoder 内存；JS heap 不能代替这些指标。rAF 间隔仅表示该机器的调度表现，不等同图片帧率或用户设备掉帧率。
- 允许播放到全部元素可见含网络/解码就绪观测开销，不能当首个动画像素变化。实际红→绿→蓝像素、有限两轮和同 URL 联动另由 `thread-cover-pixels.spec.ts` 截图验证。

## 单张旧策略与长列表对照

- 旧策略源码 `d674d399cf88ad7f4b2ebd4b7e070658522eeb39` / Build `0wU-O5ZvmH_ckuxF2UyYd` 的同素材、同扩展视口 6 组测试，每组只请求一张动画：WebP 85890 bytes 或 GIF 736785 bytes，热重挂 0；允许播放到单张元素可见冷约 312–389ms、热约 248–280ms。该旧轮未采进程内存，不能据本报告作新旧内存定量比较。
- 新策略首次并播 4/8/12 张，WebP 分别 343560/687120/1030680 bytes，GIF 分别 2947140/5894280/8841420 bytes。这组 WebP 传输少约 88.3%，但进程内存增量并没有按该比例缩小；热组基线仍保留此前分配，不能将热增量小解释为总内存低。
- 1000 张已注册历史卡片、30 次每 40ms 快滑，IO 优化前封面几何读取 58038 次；优化后同样场景两次为 243/242 次，回归限制小于 1000。实际总时间约 8022→8214/7747ms，rAF p95 约 167→200ms，最大间隔约 750→217ms。
- 几何读取减少约 99.6%，但 1000 DOM 的整体滚动/绘制成本仍显著，不能宣称长列表已经流畅。快滑中达到阈值的约 40 个 URL 会开始请求，这是无并播上限策略的已知成本。本轮没有扩大为虚拟列表实现。
